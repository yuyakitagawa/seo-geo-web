# 進捗: サイト修正提案書にディレクトリ構造を足す

`/tools/site-report` に、URLの並びから分かるディレクトリ構造の診断を足す。

## 決めたこと
- **1本も追加で取得しない**。サイトマップのURL一覧は既に取得済みなので、その文字列を数えるだけにする。
  何千本あっても実行時間と費用は変わらない（`MAX_PAGES`=8 の設計を崩さない）。
- **リンク構造は出さない**。「どのページがどこからリンクされているか」「孤立ページ」「クリック深度」は
  全ページのHTMLが要る。8ページの上限と両立しないので、**できないことをFAQに明記する**（期待させない）。
- 事実（`siteStructure.ts`）と提案文（`siteReport.ts` の `structureProposals()`）を分ける。既存の
  「判定は audit.ts、整形は siteReport.ts」と同じ切り方。
- **サイトマップから20本以上取れたときだけ**数える（`MIN_URLS`）。内部リンク由来の数十本では形が出ない。
- 役割が重なる第1階層（`/blog/` と `/column/`）は**語だけで見ている**ので断定しない。提案文に
  「中身が別物のこともある」と書き、確かめる手順を添える。

## リンク構造（2026-09-13 追記）
ディレクトリ構造に続けて、**オプション**でリンク構造も調べられるようにした。

### 決めたこと
- **既定はオフ**。チェックを入れたときだけ最大80ページをたどる。取得ページ数＝実行時間＝費用なので、
  増える実行を利用者が選んだときだけ起こす。`MAX_PAGES`=8 の設計はそのまま残る。
- **クロールしたページは `audit()` にかけない**。リンクを取るだけにして、判定は今までどおり8ページ。
  80ページ分の判定をすると、取得の待ち時間ではなくCPU時間で上限に当たる。
- **深さではなくページ数で制御する**。「5階層まで」だと、トップに100本リンクがあるサイトで
  2階層目だけで100ページ、3階層目で数千ページになり、実行時間が読めない。
- **打ち切ったら断定しない**。上限で止めた場合、その先にリンクがあったかは分からない。
  「どこからもリンクされていない」は候補として出し、`truncated` を結果に必ず載せる。
- **回数制限をこの実行だけ1分1回に絞る**（既定は2回）。
- ナビ・ヘッダー・フッター・サイドバーのリンクは「本文からの案内」に数えない。

## 上限の引き上げ（2026-09-14）
本番で1回実行した実測: **静的配信のサイトで80ページを約5秒**（並列8。1ページあたり実質0.06秒）。
期限（`CRAWL_DEADLINE_MS`=50秒）にはまるで届かず、上限のほうが先に当たっていた。
`CRAWL_MAX_PAGES` を **80 → 300** に上げた。

- 遅いサイトは上限ではなく**期限**で止まる（取れた分で提案書を作る）ので、上げてもタイムアウトのリスクは増えない
- 300なら中小規模のサイトは全ページ辿り切れることが多く、`truncated` が false になる。
  そのとき「どこからもリンクされていない」を候補ではなく**断定**して出せる（これが引き上げの主目的）
- 並列数（`CRAWL_CONCURRENCY`=8）は上げない。相手のサーバーに並べて当てすぎないため
- 所要時間の表記も実測に合わせた（「40〜60秒」→「10秒〜1分。表示の速いサイトなら300ページでも20秒前後」）

## リンク構造の図（2026-09-14）
「リンク構造も調べる」の結果に、**第1階層どうしのリンク本数のマス目**を1枚足した。

- **生のリンク図は作らない**。300ノードの力学モデル図は人が読めないうえ、描画ライブラリが要る。
  第1階層（上位8つ＋「その他」）にまとめると20〜30マスに収まり、サイトの骨格として読める
- 見せたいのは**空のマス**＝その階層から一度もリンクされていない場所（回遊が途切れている）
- 行＝リンク元、列＝リンク先。**本数はマスの中に必ず書く**ので、色が読めなくても表として成立する
- 濃さは単一色相の1段だけ。**対数**で割り当てる（ナビのリンクは全ページから出るので本数が偏る）
- 濃さの上限は60%。これ以上濃くすると、明るい配色と暗い配色のどちらかで数字が読めなくなる
  （文字色を切り替えずに両方で成立させるための上限）
- 集計は `linkGraph.ts` の `sections` / `sectionLinks`（純関数）。描画は `SiteReport.tsx` の `SectionMatrix`

## マス目を本文リンクだけに直した（2026-09-14）
最初は**全リンク**で集計して出したが、実物を見ると**読みどころが出なかった**。

原因: ナビ・ヘッダー・フッターのリンクは**全ページから同じ形で出る**。混ぜて数えると、
ナビに載っている階層の列はどの行からも埋まり、「空のマス」という読みどころが機能しない。
数字の大小も「ナビに載っているか × ページ数」でほぼ決まり、本文の設計を何も反映していなかった。

直したこと: `page.links` → `page.bodyLinks`（nav / header / footer / aside の外）。
同じファイルの別の指摘（`navOnly`）では最初から本文リンクだけを見ていたのに、マス目では混ぜてしまっていた。
見出しも「どの階層からどの階層へリンクしているか」→「本文からどの階層へ案内しているか」に変え、
ナビを数えていないことを図の説明に明記した。

これで読めるのは「記事の本文から教科書へ1本も案内していない」のような、**そのまま内部リンクの追加に繋がる事実**。
