## 結論

当サイトの運営者は、別に日本株の開示情報を扱うメディアを1つ運営しています。そちらは全ページのUser-Agentをサーバー側で記録しているので、**クローラーが実際にどの順番でページを見に来ているか**を生ログで確かめられます。

今回、そのサイトの31日分のログ——**bot判定された190,179リクエスト・17,986パス**（サイトマップ登録URLは約2,300件）——を解析しました。

結果、**sitemapの並び順では見ていません**。

連続する2リクエストがサイトマップ上で隣同士（インデックス+1）だった割合は、Googlebotで6.0%、GoogleOtherで3.4%、ClaudeBotで1.2%。セッション内の巡回順とサイトマップ順の順位相関（Spearman）は全botで **ρ = 0.00〜+0.11**、つまり無相関です。前方向に進む割合も約50%で、方向すらありません。

代わりに見えたのは、次の3層構造でした。

この構造から出てくる実務的な帰結は2つです。どちらも「サイトマップをどう書くか」ではなく、**サイトの作りそのもの**の話になります。

**1つめ。AIクローラーにとって、内部リンクは補助ではなく唯一の経路です。** ClaudeBotは31日間で2,257パスを取得していますが、ページURLが列挙されたファイルを1度も読んでいません（取得したのはサイトマップの索引だけで、子サイトマップは0回）。GPTBotも同じです。

**2つめ。ディレクトリは「一気見される単位」なので、中身が揃っていないとバーストが丸ごと無駄になります。** このサイトでは、旧URL形式と死んだURLが溜まった2つのディレクトリ（`/investors` と `/en`）だけで **bot全リクエストの35.8%** を吸っていました。その大半はリダイレクトか404に消えています。

以下、順に実データを出します。

## 何をどう測ったか

Next.jsの `proxy`（旧middleware）で全リクエストのUser-Agentを判定し、`path` / `bot_name` / `occurred_at` をデータベースに記録しています。今回はそのうちブラウザ判定を除いたbotの行だけを取り出し、**30分以上の間隔が空いたら別セッション**として区切って解析しました。

サイトマップ側は、実際に配信されている `/sitemap.xml`（sitemapindex）と、そこから参照される5本の子サイトマップを取得し、`<loc>` の出現順をそのままインデックス番号にしています。

なお、この判定はUser-Agentの自己申告に基づくもので、逆引きDNSでの検証はしていません。ログ全体のうちスキャナー由来と見られる怪しいパス（`/.git/config`、`/.env` など）は133件で、全体の0.07%でした。

## 検証1: sitemap順で見ているか → ノー

各botについて、連続する2リクエストの両方がサイトマップに載っているケースだけを取り出し、インデックス番号の差を数えました。

| bot | 対象ペア数 | 差が+1（次の行） | 差が-1（前の行） | 前方向に進んだ割合 |
| --- | ---: | ---: | ---: | ---: |
| GoogleOther | 58,580 | 3.4% | 6.0% | 35.3% |
| Googlebot | 1,621 | 6.0% | 2.1% | 52.0% |
| OAI-SearchBot | 3,355 | 2.1% | 2.3% | 49.4% |
| AhrefsBot | 1,369 | 1.5% | 0.9% | 54.2% |
| MJ12bot | 1,258 | 1.7% | 2.7% | 38.1% |
| PerplexityBot | 922 | 0.9% | 1.0% | 49.9% |
| ClaudeBot | 243 | 1.2% | 0.8% | 46.1% |

サイトマップに2,255件のURLがあるので、完全にランダムなら「差が+1」は0.04%です。数%は出ていますが、順番に読んでいるなら数十%になるはずの値です。前方向の割合が軒並み50%前後という点も、方向を持って読み進めていないことを示します。

さらにセッション単位で、巡回順とサイトマップ順の順位相関を取りました。子サイトマップ内で20件以上を取ったセッションだけを対象にした中央値です。

## 検証2: どこから入ってくるか → botごとに全く違う

セッションの先頭1本が何だったかを数えると、botの性格がはっきり分かれました。

| bot | セッション数 | robots.txtから始まる | sitemap.xmlから始まる |
| --- | ---: | ---: | ---: |
| MJ12bot | 119 | 100.0% | 0.0% |
| ClaudeBot | 95 | 73.7% | 17.9% |
| Googlebot | 308 | 56.2% | 2.9% |
| SemrushBot | 168 | 47.6% | 0.0% |
| AhrefsBot | 186 | 18.8% | 57.0% |
| GPTBot | 38 | 0.0% | 81.6% |
| GoogleOther | 230 | 0.0% | 0.0% |
| ChatGPT-User | 389 | 0.0% | 0.5% |
| Amazonbot | 90 | 0.0% | 0.0% |

GPTBotは**robots.txtを31日間で1度も取っていません**が、8割のセッションを `/sitemap.xml` から始めています。robots.txtを長期キャッシュしていると考えるのが自然です。

対照的に、**ChatGPT-User（ユーザーがChatGPTで質問したときに走る取得）は389セッション中387回、いきなり本文ページ（トップページ含む）に来ています**。入口の概念がなく、必要な1ページだけを取りに来る挙動です。GoogleOtherとAmazonbotも同じくrobots.txt・sitemapを一切踏みません。

Googlebotは逆で、**自分のリクエストの15.4%（10,942件中1,687件）がrobots.txt**でした。SemrushBotも11.6%。robots.txtの応答速度が巡回全体の速度に効くタイプのbotが実在するということです。

## 検証3: 塊の中は何順か → 自前のキュー順

ClaudeBotの最長セッションが分かりやすい例でした。

```
+     0.0s  /robots.txt
+     1.7s  /sitemap.xml
+   842.2s  /stocks/3950     ← 14分の沈黙のあと
+   842.2s  /stocks/8136
+   845.5s  /stocks/3733
+   845.5s  /stocks/6902
+   847.0s  /stocks/4641
   （以下 /stocks/ が735件連続）
```

その1時間前のセッションは `/investors/` を627件連続、別の日は英語版記事を219件連続。**1セッション＝1つのURL種別**という切り方をしています。同じ種別が次に来る確率は87.4%で、ランダムに並べ替えた場合の26.2%を大きく上回ります。

そして塊の中の順番は、銘柄コード順でもサイトマップ順でもありません。決定的だったのは次の2点です。

サイト側が影響できるのは「行列に何を入れるか」だけ、というのがこの解析の実務的な結論です。

## 副産物1: ClaudeBotとGPTBotは子サイトマップに降りていない

31日間の `/sitemap*` 取得を全部数えました。

ClaudeBotが2,259パス、GPTBotが1,380パスを取れているので、リンク経由では発見できています。ただ「サイトマップを置いたからAIクローラーに全URLを伝えられている」という前提は、少なくともこの2つのbotについては成り立ちません。

## では何が効くのか: リンク構造とディレクトリ

並び順が効かないなら、サイト側に打つ手はないのか。ログを見る限り、効くのは**「待ち行列に何が入るか」**と**「URLがどう束ねられるか」**の2つです。

### 1. AIクローラーのURLは、ほぼリンク経由でしか入っていない

ClaudeBotが31日間で取得したパスは2,257件（robots.txtとサイトマップを除く）。一方でClaudeBotが取得したサイトマップは `/sitemap.xml`（インデックス）だけで、**そこに書かれているのは子サイトマップ5本のURLだけ**です。ページのURLは1件も載っていません。子サイトマップは0回。

つまりClaudeBotは、**ページURLが列挙されたファイルを1度も読んでいないのに、2,257パスを知っている**ことになります。発見経路はリンク（内部リンクか、外部からの参照）以外にありません。GPTBotも同じ構図で、1,379パスを取得しながら子サイトマップは0回です。

サイトマップが届いていないbotにとって、内部リンクは補助ではなく**唯一の経路**です。「サイトマップに載せたから大丈夫」は、AIクローラーに対しては成り立ちません。

### 2. 巡回はディレクトリ単位で束ねられている

第2層で見た「URL種別ごとの一気読み」は、URLの第1階層（ディレクトリ）で切ると、より鮮明になります。

| bot | 次のリクエストが同じディレクトリ | ログをランダムに並べ替えた場合 |
| --- | ---: | ---: |
| MJ12bot | 95.3% | 38.1% |
| ClaudeBot | 87.5% | 26.1% |
| AhrefsBot | 71.2% | 40.6% |
| GPTBot | 68.2% | 27.1% |
| PerplexityBot | 67.1% | 27.6% |
| Googlebot | 51.0% | 15.7% |
| GoogleOther | 40.5% | 9.8% |

これはGoogleの公式ドキュメントの記述とも一致します。SEOスターターガイドは、似た話題のページをディレクトリにまとめると、Googleがディレクトリ単位で更新頻度を学習し、**ディレクトリごとに異なる頻度でクロールできるようになる**と書いています（数千URLを超えるサイト向けの記述）。

ログで見えたのは、その挙動がGooglebotだけでなく、ClaudeBot・GPTBot・PerplexityBotでも同じように出ているということです。

裏を返すと、**更新頻度の違うページを同じディレクトリに混ぜると損をします**。毎日更新のページと1年変わらないページが同居していると、ディレクトリ単位の頻度学習が効かなくなるからです。

#### 第1階層を増やすべきか、束ねて第2階層を厚くすべきか

ここで実務的に迷うのが、ディレクトリを第1階層に横並びで増やすか、束ねて第2階層を厚くするか、です。

結論から言うと、**束ねる側のデメリットは観測できませんでした**。botが束ねている単位は「第1階層」ではなく、**実際に同種のページをまとめている階層**だったからです。

このサイトには `/en/articles/<id>`・`/en/category/<name>` のように、第1階層1つの下に第2階層が並ぶ構造があります（31日間で21,803リクエスト）。ここでbotが第2階層ごとに束ねているかを測りました。

| bot | `/en/` 内で同じ第2階層が次に来る | ログをランダムに並べ替えた場合 |
| --- | ---: | ---: |
| MJ12bot | 95.3% | 49.4% |
| AhrefsBot | 76.4% | 51.7% |
| Googlebot | 75.6% | 45.6% |
| GPTBot | 69.6% | 32.4% |
| GoogleOther | 58.5% | 32.2% |
| OAI-SearchBot | 45.2% | 31.5% |

**第1階層が1つに束ねられていても、botは第2階層で束ねて読んでいます。** 「まとめると一気見の単位が壊れる」という心配は要りません。

逆に、第1階層を増やすことの利得を示す数字は出ませんでした。Googleがディレクトリを推す理由は更新頻度の学習なので、**更新頻度が同じものを第1階層で割っても、学習される情報は増えません**。

なお、このサイトは第3階層が `/en` 配下にしか存在せず、4階層以上のデータがありません。**深い入れ子が不利かどうかは、今回のログでは検証できていません。**

### 3. 一気見されるからこそ、ディレクトリの中身がそのまま結果になる

ディレクトリ単位でまとめて読まれるということは、**そのディレクトリに何が入っているかが、そのままクロールの成果になる**ということです。良いものが入っていれば全部拾われ、ゴミが入っていればゴミを拾って帰ります。

同じサイトのディレクトリ別に、サイトマップ掲載URL数と、実際にbotが叩いたユニークURL数を並べました。

| ディレクトリ | sitemap掲載 | 実際に叩かれたURL | うちsitemap外 | リクエスト中のsitemap外率 |
| --- | ---: | ---: | ---: | ---: |
| /investors | 538 | 10,036 | 9,501 | 72% |
| /en | 0 | 2,034 | 2,034 | 100% |
| /stocks | 667 | 4,082 | 3,415 | 53% |
| /articles | 917 | 1,401 | 508 | 34% |
| /date | 81 | 232 | 152 | 31% |
| /faq | 10 | 10 | 0 | 0% |
| /category | 14 | 26 | 12 | 0.3% |

`/category` のsitemap外12URLは、31日間で合計13リクエストしか受けていません。

`/investors` は、サイトマップに載せているのが538件なのに、**実際には10,036件のユニークURLが叩かれています**。中身を見ると内訳はこうでした。

- **7,115件** が旧URL形式（`/investors/加藤産業株式会社`）。現在は `/investors/2925` へ308リダイレクトされる
- **2,386件** がサイトマップに無い数字ID（`/investors/9999` など）。404が返る

このディレクトリへのリクエストは31日間で35,528件、**bot全リクエストの18.7%**。そのうち72%が、リダイレクトか404に消えています。

`/en` はさらに極端で、**32,608リクエスト（bot全体の17.1%）が、サイトマップに1件も載っていないディレクトリに入っています**。現在このパスはトップページへ308リダイレクトされます。過去に存在した英語版の残骸を、botが待ち行列に持ち続けているということです。

対して `/faq`（10件）と `/category`（14件）は、サイトマップと実URLがほぼ一致しています。カバー率もGooglebot・GoogleOtherともに100%です。

## この解析の限界

標本は1サイト・31日分です。サイトの規模（約2,300URL）、更新頻度（ほぼ毎日）、ジャンル（日本株の開示情報）に依存する結果が混じっている可能性があります。

とくに次の3点は、他サイトで同じになるとは限りません。

- **GoogleOtherの比率の高さ**。57.6%は明らかに偏っており、このサイト固有の事情がある可能性があります
- **ClaudeBotの最終アクセスが2026-08-21で止まっている**こと。以降の12日間、1件も来ていません
- **子サイトマップの未取得**。分割の仕方（5本／最大916URL）やインデックスの記述による可能性を排除できていません

また、突き合わせに使ったサイトマップは**期間の最終日に取得したスナップショット**です。期間中に並び順が変わっていた可能性は排除できません。ただし、相関がゼロという結果はbot・セッション・期間を通じて一貫しており、並び順の変化だけでは説明しきれません。

User-Agentの逆引きDNS検証もしていないため、botを詐称したアクセスが混じっている可能性も残ります。怪しいパスへのアクセスは全体の0.07%でした。

一方で「サイトマップの並び順と巡回順が無相関」という点は、bot・セッション・期間を問わず一貫して出ました。ここは他サイトでも再現しやすいと考えています。

## よくある質問

### サイトマップの先頭に重要なURLを置く意味はありますか

今回の31日分のログでは、サイトマップの掲載順と実際の巡回順に相関はありませんでした。重要なURLは順番で示すのではなく、一覧・カテゴリページからクロール可能なリンクで到達できる状態にしてください。

### AIクローラーはサイトマップを読まないのですか

クローラーによって異なります。今回のサイトではClaudeBotとGPTBotがサイトマップインデックスを取得した一方、参照先の子サイトマップは取得していませんでした。GooglebotとBingbotは子サイトマップまで取得しています。

### ディレクトリを浅くすれば巡回が増えますか

今回のデータだけでは断定できません。2階層と3階層の差には、言語やページの優先度も混ざっています。階層の深さより先に、同じ種類・更新頻度のページをまとめ、旧URLや404を減らしてください。
