## 結論

Core Web Vitalsは、LCP・INP・CLSの3指標すべてが75パーセンタイルで基準値を満たせば直す必要はありません。
基準値は、LCPが2.5秒以内、INPが200ミリ秒以下、CLSが0.1以下です。
すでに3指標が基準を満たしているページに対して、Lighthouseのスコアを100点にする作業を続けているなら、それは今日やめるべきです。

## Core Web Vitalsとは何か

Core Web Vitalsは、Googleが提唱する「すべてのWebページに適用され、すべてのサイト運営者が計測すべき」とされる品質指標の集合です。
ページの読み込み・操作への反応・見た目の安定性という3つの観点から、ユーザー体験を数値化します。
LCP（Largest Contentful Paint）は読み込み、INP（Interaction to Next Paint）は操作への反応、CLS（Cumulative Layout Shift）は見た目の安定性を測ります。

この基準値は「75パーセンタイル」で判定します。
ページ閲覧の75%がこの基準に収まっていれば合格とみなし、モバイルとデスクトップは分けて評価します。
3指標のうち1つでも75パーセンタイルで基準を外れていれば、そのページは不合格として扱われます。

Core Web Vitalsに含まれる指標は固定ではなく、experimental（実験的）、pending（確定前）、stable（安定）という3段階のライフサイクルを経て入れ替わります。
現にINPは2023年にpendingへ、2024年にstableへ昇格し、それまでCore Web VitalsだったFID（First Input Delay）を置き換えました。
stable段階の指標は年1回より高い頻度では変更されない、とされていますが、将来的な指標の追加・入れ替わりはありうる前提で運用します。

<FigureQuote
  text="Site owners shouldn't have to be performance experts to understand the quality of experience they are delivering to their users."
  source="web.dev「Web Vitals」Philip Walton, 2024年10月31日更新"

「サイト運営者はパフォーマンスの専門家にならなくても、自分のサイトの体験の質を理解できるべきだ」という意味です。
だからこそ合否判定はシンプルな3指標と1つの基準値（75パーセンタイル）に絞られています。
細かいサブ指標まで全部追いかける必要はない、という設計思想がこの一文に表れています。

最初の手順は、Chrome User Experience Report（CrUX）のデータに基づくツールを見ることです。
CrUXはユーザーの実際の閲覧から匿名で収集したデータで、Chrome DevTools・PageSpeed Insights・Search ConsoleのCore Web Vitalsレポートの元になっています。
Search Consoleのレポートの読み方は[Google Search Consoleの使い方。最初に見る4つのレポートと数字の読み方](/articles/36)で確認できます。

2番目の手順では、3指標をモバイルとデスクトップで別々に75パーセンタイル判定します。
片方の環境だけ基準を満たしていても、もう片方が外れていれば、その環境向けの対応が必要です。

3番目と4番目の手順では、不合格の指標だけをLighthouseやChrome DevToolsで深掘りします。
Lighthouseはシミュレーション環境でページを読み込むため、ユーザー操作が存在せず、INPを直接測れません。
代わりにTBT（Total Blocking Time）というラボ専用の指標をINPの代理として使います。
TBTを改善する施策はフィールドのINPを改善することがありますが、ラボ環境だけで合否を判断してはいけません。

5番目の手順は、不合格指標ごとに用意された改善ガイドの適用です。
LCP・INP・CLSにはそれぞれ専用の改善ガイドがあり、その指標固有の原因に対応した施策が並んでいます。
全指標に共通する万能の一手は無いため、指標ごとに原因を切り分けてから着手します。

6番目の手順は、継続的なリアルユーザー計測の設置です。
web-vitalsというJavaScriptライブラリを使うと、onCLS・onINP・onLCPといった関数を呼ぶだけで各指標を計測し、自社の分析基盤に送信できます。
CrUXは集計に時間がかかり、ページ単位の詳細な診断には向かないため、自前のリアルユーザー計測を別途持つことが推奨されています。

## やること／やらなくていいこと

  title="Core Web Vitals対応でやること・やらなくていいこと"

  ]}
  donts={[
    "すでに基準を満たしている指標のスコアをさらに上げる作業",
    "Lighthouseのラボスコアだけで合否を決める作業",
  ]}
/>

3指標すべてが75パーセンタイルで基準を満たしているページに追加の速度改善を重ねても、合否区分は変わりません。
Core Web Vitalsの判定はツール側も「3指標すべてが目標値に達しているか」の二値で見るため、基準超過分の積み増しは評価上の意味を持ちにくい作業です。
その工数は、不合格のページや指標に振り向けたほうが費用対効果は高くなります。

Lighthouseはページ開発中の回帰検知には有効ですが、シミュレーション環境での計測であるため、実際のユーザー環境のばらつきを反映しません。
デバイス性能・通信環境・同時に動く他のプロセス・ユーザーの操作方法によって指標の値は変わります。
ラボのスコアを100点にする作業だけを続けても、フィールドでの合否が改善するとは限りません。

### 日本の業種での具体例

例えばアパレル系ECサイトで、商品一覧ページのLCPがモバイルの75パーセンタイルで3.2秒だったとします。
基準の2.5秒を超えているため、まずはLCP専用の改善ガイドに沿って、一覧ページの画像読み込みを見直す対応が優先です。
同じサイトでCLSがすでに0.05で基準の0.1を満たしているなら、CLS側への追加工数は後回しにしてかまいません。

例えばBtoBの資料請求サイトで、問い合わせフォームのあるページだけINPがデスクトップで250ミリ秒だったとします。
基準の200ミリ秒を外れているため、フォーム送信時の処理やサードパーティタグの実行を疑って、Chrome DevToolsで原因を特定する対応が必要です。
他のコーポレートページのINPがすでに基準内なら、そちらに同じ対応を横展開する優先度は低くなります。

サイト全体の修正順位を機械的に洗い出したい場合は、[サイト修正提案書](/tools/site-report)で不合格ページを先に絞り込む方法もあります。

計測の仕組みそのものを体系的に学びたい場合は、[教科書レッスン11「計測と改善サイクル」](/learn/measurement)が手順を扱っています。

## よくある質問

### モバイルとデスクトップ、どちらを優先して見るべきですか

優先度は書かれていませんが、Core Web Vitalsの合否はモバイルとデスクトップを分けて判定する仕組みです。
片方だけ不合格ならその環境向けの対応に絞り、両方とも不合格なら両方に対応が必要です。

### INPが新しい指標になった経緯を教えてください

INPは2023年にpending、2024年にstableへ昇格し、以前Core Web VitalsだったFID（First Input Delay)を置き換えました。
FIDは操作が始まった瞬間までしか測れませんでしたが、INPは操作が終わり画面が更新されるまでの反応全体を測ります。

### ラボ環境でINPが測れないのはなぜですか

Lighthouseなどのラボツールはページをシミュレーション環境で読み込むため、実際のユーザー操作が存在しません。
INPは操作への反応を測る指標なので、操作が無いラボ環境では直接測定できず、代わりにTBTを代理指標として使います。
